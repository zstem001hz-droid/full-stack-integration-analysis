## 1. CORS Explained

A CORS error occurs when a browser enforces the Same-Origin Policy and blocks a request made from one origin to a resource at a different origin. In a typical MERN stack setup where the React client and Express server are maintained in separate repositories — and run on separate ports during local development — this happens almost immediately. A React app served at `localhost:5173` making a fetch call to an Express API at `localhost:5000` is crossing origin boundaries, because origin is defined by the combination of scheme, hostname, and port. The browser intercepts that request before it reaches the server and rejects it. Importantly, this is a browser-enforced restriction — the same request made from Postman or curl succeeds without issue because those tools don't implement the Same-Origin Policy.

Two strategies exist for handling this during local development. The first is configuring CORS on the Express server itself using the `cors` npm package. By passing an options object with the client's origin explicitly listed, Express adds the appropriate `Access-Control-Allow-Origin` response header, and the browser permits the request. This is a valid approach, but it requires the server to be updated and restarted any time the allowed origin changes. The second strategy — and the more seamless one for development — is setting up a proxy on the frontend dev server. In Vite, this is configured inside `vite.config.ts` by mapping any request to `/api` forward to the backend's port. The browser only ever communicates made from the browser's perspective, and CORS never triggers. The proxy strategy is development-only and requires a proper CORS configuration before the application reaches production.

## 2. Environment Management

Hardcoding an API URL like `http://localhost:5000` directly into a React component creates two compounding problems. The first is inflexibility — that URL is different in every environment: local development, staging, and production all point to different servers. Every environment change requires a manual code edit and a new deployment. The second is exposure. Client-side JavaScript is not private. Anything written into a React component is bundled, sent to the browser, and readable by anyone who opens DevTools. Hardcoding internal server addresses, and especially API keys, into component code is a security risk that becomes a liability the moment the application is publicly accessible.

Environment variables address both of these concerns. On the server side, the `dotenv` package reads a `.env` file at startup and injects its key-value pairs into `process.env`, making configuration data available throughout the Node.js process without it ever appearing in source code. The `.env` file is added to `.gitignore` and kept off version control entirely. On the client side, Vite exposes environment variables prefixed with `VITE_` through `import.meta.env` at build time — only variables with that prefix are bundled into the client output, preventing accidental exposure of server-side secrets. A `.env.example` file committed alongside the codebase documents which variables are required without exposing their actual values, giving any developer joining the project a clear. contract for what needs to be configured locally.

## 3. Data Fetching Trade-offs

The most consequential difference between `fetch` and `axios` in a complex application is how each handles HTTP error responses. The native `fetch` API only rejects its promise when a genuine network failure occurs — a DNS resolution failure, a dropped connection, or a request that never reaches the server. A response that comes back with a `404 Not Found` or a `500 Internal Server Error` status code is considered a resolved promise by `fetch`. The developer is responsible for checking `response.ok` manually on every single call and throwing an error if the status code falls outside the 2xx range. In a codebase with multiple API calls across many components, this becomes repetitive and is easy to forget — a missed check means a failed request silently passes through to state as if it succeeded.

`axios` throws an error automatically for any response with a 4xx or 5xx status code, which means `.catch()` blocks and `try/catch` wrappers actually capture server errors without any manual status inspection. Beyond error handling, `axios` also supports interceptors — middleware that can be attached to every outgoing request or incoming response globally. For a complex application where every authenticated request needs an `Authorization` header attached, an interceptor handles that in one place rather than duplicating the header logic across every call site. This combination of automatic error promotion and centralized request/response handling makes `axios` considerably more maintainable as an application's API surface grows.
